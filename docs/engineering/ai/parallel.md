# Parallel work

Several agents work at the same time. This page explains how their work comes together without conflicts.

**Status:** <Badge type="info" text="DESIGN" />

[[toc]]

## 1. Branches

| Branch | Lifetime | Pushed | Owner |
|---|---|---|---|
| `main` | Permanent | Yes | Human. One squash commit per WP. |
| `wp/<WP-ID>` (integration) | One WP | Only as a backup between sessions | Architect |
| Lane worktree branch | One task | Never | One subagent |

::: warning Cloud sessions are temporary
A cloud container can be removed when the session is idle. Push `wp/<WP-ID>` at the end of each sprint so that no work is lost. Delete it after the WP is squashed into `main`.
:::

## 2. Before the lanes start

1. The architect creates `wp/<WP-ID>` from `main`.
2. The architect commits the **contracts** on `wp/<WP-ID>`: types, traits, interfaces, error codes, fixtures, empty test files with test names, and stubs that compile.
3. The architect writes the **ownership table** in the sprint record. Each path belongs to one lane.
4. The architect commits the sprint record. Lane worktrees start from this commit (`worktree.baseRef: "head"` in `.claude/settings.json`).

## 3. Ownership

| Rule | Reason |
|---|---|
| One path, one lane | Two lanes never change the same file |
| Shared files belong to the architect | Manifests, lock files, `config.mts`, `AGENTS.md`, `CLAUDE.md`, `.claude/`, status tables change in one place |
| A lane that needs a shared change writes a **shared-file request** in its report | The architect applies it during integration |
| New files go under the lane's own folders | No naming collisions |
| Generated files are regenerated by the architect after merge | Lock files and generated code never conflict |

Example ownership table:

| Lane | Tier | Owns | Reads |
|---|---|---|---|
| L1 markup parser | Senior | `crates/rivqen-template/src/markup/**`, its tests | `crates/rivqen-integrity/**` |
| L2 header codec | Middle | `crates/rivqen-proto/src/headers/**`, its tests | `crates/rivqen-integrity/**` |
| L3 fixtures | Junior | `fixtures/rqp/markup/**` | Spec pages |
| L4 docs | Docs steward | `docs/engineering/protocol/markup.md` | Lane reports |

## 4. Run the lanes

1. Start each lane as a subagent with worktree isolation.
2. Give each lane its brief: goal, owned paths, contracts, checks, docs to update.
3. Start lanes with no dependencies at the same time. Start a dependent lane after its input is integrated.
4. Keep at most **4** code lanes at the same time. More lanes cost more review time than they save.

## 5. Integrate

Integrate one lane at a time, in dependency order.

1. Read the lane report. Reject a report without test results.
2. Check that the lane changed only its owned paths: `git diff --stat wp/<WP-ID>...<lane-branch>`.
3. Merge the lane into `wp/<WP-ID>` (`git merge --no-ff <lane-branch>`).
4. Apply the shared-file requests. Regenerate lock files.
5. Run the fast checks for the affected packages.
6. If a check fails, send the lane back with the failure. Do not fix it in the architect session unless the fix is one line.
7. Remove the worktree and the lane branch.

## 6. If a conflict happens

A conflict means the ownership table was wrong.

1. Stop the integration.
2. Find the shared path and assign it to one lane or to the architect.
3. Resolve the conflict with the owner's version. Re-apply the other change as a request.
4. Add the path to the shared-file list in the sprint record.
