| Q-23 | Keyed revisions (HMAC, [manifest and patch §1.3](/engineering/protocol/manifest-patch#_1-3-hashes-and-revisions), rule 4) and the client checks. After H-103, H-104, H-107 and H-108 the only server values that the client checks by its own computation are `page_revision` of the manifest and `binding` of a delta: both are unkeyed SHA-256 values that the client computes from its markup analysis, its snapshot, the URL and the nonce of its request. A client cannot compute a keyed value. The binding needs a base B that both sides know exactly: the server takes B from `If-None-Match`, the client puts the page revision of its snapshot. When WP-18 keys the header validators (`ETag`, `If-None-Match`), the client sends a keyed tag that it cannot compute; then either the client binds the exact tag text that it sent (it stores the tag of F with the snapshot, and the preimage encodes the tag injectively: a length or a fixed form, never a free text next to LF), or WP-18 defines another source of B that both sides know (S6 security re-review B4). The nonce N of H-108 is not keyed and is no key: it binds a delta to one request, not to a secret. WP-18 MUST keep a value that the client can compute in the body (the manifest and the delta envelope), and a check with the same coverage as today (the base, the URL, the request and the result; S6 security review F5) | Design of the keyed revisions; a check that each client check of manifest-patch §1.8 item 5 and §2.4 step 7 keeps its coverage, with a known-answer test for the B encoding | Keyed revisions for private pages (H-8, H-60) | WP-18 |
| Q-24 | URL and nonce interop of the native clients (S6 security re-review B5). U of the binding is the WHATWG serialization of the final URL ([manifest and patch §2.2](/engineering/protocol/manifest-patch#_2-2-fields)); the URL types of OkHttp, `java.net.URI` and `URLComponents` can write other bytes for the same URL, for example for `'`, `\|`, `^`, `` ` ``, `{` and `}` in the query, for a host with a trailing dot (`a.example.`), and for a percent-encoded unreserved character. A difference gives `INTEGRITY_ERROR` and one full load on every delta navigation of that URL: never a wrong page, but no delta. Also: (a) a server that reads the request target behind a proxy that rewrites the query; (b) the field `Rq-Nonce` that an intermediary changes, removes or duplicates (no delta); (c) a delta that an intermediary stores against `no-store`, or gives to concurrent requests for one URL (CDN request collapsing): an RQP client rejects it (`INTEGRITY_ERROR`), but a load without RQP shows its body as data (S6 final security review L1, I2; DL-063); (d) a network stack that repeats an attempt with the same `Rq-Nonce` (review I1: the SDK sets the nonce for each network attempt and checks the nonce of the request of the final response). Repeated `INTEGRITY_ERROR` for one origin SHOULD trip the per-origin kill switch of the SDK ([vulnerability management](/engineering/security/vulnerability-management), A-10 of [Android](/engineering/platforms/android)), so that a serializer difference costs one full load per navigation only until the switch acts, and the metric shows it | Interop fixtures: each native client serializes a list of URLs with these characters and hosts, and its binding must match the reference (or the SDK serializes U with a WHATWG-conformant function of its own); a threshold and a time window for the kill switch; the intermediary test of [negotiation §11](/engineering/protocol/negotiation#_11-intermediaries) checks that `Rq-Nonce` passes unchanged as one field line, that a delta (D) is never stored or collapsed (CDN request collapsing of concurrent requests for one URL; DL-063), and that `X-Content-Type-Options: nosniff` and `Vary: Rq-Nonce` of D arrive; the SDK test checks a new nonce for each network attempt | Delta rate of native clients; WP-13 intermediary matrix | WP-13 (with WP-04, WP-10) |
