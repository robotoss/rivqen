### Human decisions

| ID | Question | Decision |
|---|---|---|
| H-131 | When may the SDK make a native early fetch with the cookies of the store (the native path does not apply SameSite)? | **App-started loads plus page-started navigations with proven same site** (human, 2026-11-08): (1) a load that the app starts, when the web view is blank or shows the same origin as the target; (2) a navigation that a page starts, when the `Referer` origin (Android) or the `sourceFrame` origin (iOS) proves the same site; no proof means no early fetch. Same site: see H-132. Rejected: early fetch for app-started loads only (less acceleration), cookie filtering in the SDK (re-implements browser rules). Recorded in [HTTP stacks](/engineering/transport/http) §2 |
| H-132 | How does the SDK decide "same site" for H-131? An SDK copy of the Public Suffix List gets old; an old list can call two sites one site where the current WebView calls them two (a SameSite=Strict bypass) | **Equal origin, or origins that the app declares as one site in its configuration** (human, 2026-11-08). The app can update the list remotely, without a release; a domain that is not in the list only loses the early fetch. No Public Suffix List, no new dependency. Rejected: a Public Suffix List with signed remote updates (update channel, MPL-2.0 dependency, a window between a list change and the update), equal origin only (no early fetch between declared subdomains) |
