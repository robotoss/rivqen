| H-6 | G1 scope | Parser candidates in **all four languages** (Rust, Node.js, Java, PHP) in WP-17, with a differential test. | This record |
| H-7 | Q-17-1: patch base | **Client sends its block digests** in a request header; a stateless server sends only changed blocks. **Fallback:** without the header (or when it is too large) the server sends all blocks when the template revision matches (VasSonic behavior). No server history. | Spec (WP-17) |
| H-8 | Q-17-2: revisions | **Normative, content-derived** for servers: `t1.` + base64url SHA-256 of the template, `r1.` + base64url SHA-256 of a defined preimage; full length (46 characters). Clients treat revisions as opaque. A keyed (HMAC) variant for private pages is decided in WP-18. | Spec (WP-17) |
| H-9 | Q-17-4: `page_id`, `sequence` | **Push channels only** (P8). The HTTP patch envelope has neither field. | Spec (WP-17); WP-16 |
| H-10 | Hash per patch operation | **Keep** the block hash in each operation. Server cost: the same hash is already computed for the manifest and the revision. | Spec (WP-17) |
| H-11 | Q-17-3: envelope and `json` hash | **JSON envelope.** Block content is always a JSON **string**; the hash is SHA-256 over the UTF-8 bytes of that string. **JCS is dropped.** Binary encodings (deterministic CBOR) only later, as an option, after measurement. Security of the format is the same: confidentiality and protection against tampering come from TLS; the hash checks integrity only. | Spec (WP-17) |
| H-12 | Q-17-6: block without an explicit end tag | **Invalid for RQP.** Also invalid: void elements and other forbidden elements. The server sends the original document without a manifest. | Spec (WP-17) |
| H-13 | Q-17-5: PHP parser candidate | **Own small tokenizer in PHP** (WHATWG tokenizer subset, byte offsets, no tree), in WP-17. Senior lane, fuzzing, security review, differential test. | Sprint plan |
| H-14 | Docs toolchain advisories (`vite` 5.4.21, `katex` 0.16.47) | Separate `chore/docs-deps` change **after** WP-17. Until then, do not expose `docs:dev` to a network. | R-17-4 |

### Research results (kickoff)

| ID | Topic | Result |
|---|---|---|
| R-1 | Exact inner-content offsets in HTML parsers | Rust `lol_html` 3.0.1 (BSD-3-Clause): byte spans of start and end tags. Node.js `parse5` 8.0.1 (MIT): `startTag.endOffset`, `endTag.startOffset` (UTF-16 units). Java `jsoup` ≥ 1.23.2 (MIT): `sourceRange()`, `endSourceRange()` (UTF-16 units; `isImplicit()` for implied end tags). **PHP: no library with a public byte-offset API** (`Dom\HTMLDocument` gives line numbers only; `masterminds/html5` gives nothing). Implied end tags give different results in each parser. |
| R-2 | JCS, Structured Fields, JSON Schema libraries | JCS: libraries exist for Rust, Java, JS, PHP; **no Swift library**; number serialization is the main risk. Structured Fields: Rust `sfv` 0.16.0, Node `structured-headers` 2.1.0, Java `org.greenbytes.http:structured-fields` 0.6, Swift `apple/swift-http-structured-headers`; PHP support for RFC 9651 not verified (RQP needs only Integer, String, inner list of tokens). JSON Schema 2020-12: Rust `jsonschema`, Node `ajv`, Java `networknt`, PHP `opis/json-schema`. Base64url decoders differ in strictness (Node.js and PHP are lenient). |
| R-3 | npm supply-chain incidents and lock files | No package from the 2025–2026 incident lists (chalk/debug, Shai-Hulud waves, nx, axios, TanStack, AntV, keyv/cacheable) is in either lock file. Pin list for P1: `parse5` 8.0.1, `htmlparser2` 12.0.0, `structured-headers` 2.1.0, `ajv` 8.20.0 (+ `fast-uri` ≥ 3.1.3), `ajv-formats` 3.0.1, `vitest` 5.0.3, `@stryker-mutator/core` 10.0.0 (check that `chalk` resolves to ≥ 5.6.2). Install with `npm ci --ignore-scripts`. npm 10.9 has no `min-release-age` (npm ≥ 11.10). Docs toolchain: `vite` 5.4.21 (via `vitepress` 1.6.4) has dev-server advisories without a 5.x fix; `katex` 0.16.47 has a Low advisory. Static build output is not affected. |
| R-4 | Patch base, revisions, `page_id`/`sequence`: VasSonic design vs modern options | VasSonic: the server keeps no state and knows only "template hash equal or not"; it sends **all** data blocks; the **client** diffs (`upstream:sonic-android/sdk/src/main/java/com/tencent/sonic/sdk/SonicUtils.java:271-299`). `etag` and `template-tag` are SHA-1 hex of the rendered HTML and of the template (`upstream:sonic-java/src/main/java/com/github/tencent/SonicFilter.java:93, 119`): content-derived, so instances agree. No session id on the wire, no replay or order protection. Modern options compared: stateless all-blocks, stateful history, client block digests, content-addressed block URLs, manifest-first fetch, RFC 9842 dictionaries, LiveView, Turbo Streams, RSC. Recommendation: client digests with all-blocks fallback; normative full-length SHA-256 revisions (`t1.`/`r1.`); `page_id`/`sequence` only on push channels. Spec defects found: no `page_id` source (R1), demo `sequence` is a per-path server counter (R3), 64-bit demo revisions (R5), hex vs base64url (R6), demo history mixes users (R7), same strong ETag for two representations (R8). |
| R-5 | Compact wire formats (protobuf, CBOR, MessagePack) vs JSON | Recommendation: **keep JSON** for rqp/1. Size split of the measured 869 B patch: hashes 29 %, content 9 %, keys and syntax 49 %. After brotli the hash encoding changes almost nothing; raw size matters because small responses are often not compressed (CloudFront compresses only ≥ 1000 B). Protobuf output is not canonical → never hash it. Deterministic CBOR or an own length-prefixed frame are the only binary candidates; defer as an optional capability after measurement on real pages. Biggest saving without a new format: no per-operation hash when integrity comes from `next_revision` (≈ 270–290 B br, legacy 253 B; estimate). Hash raw block bytes for both formats and drop JCS (spec and demo disagree today). |
