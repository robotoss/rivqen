### Research R-6 (2026-10-12)

<Badge type="warning" text="RESEARCH" /> Request header limits: about 8 KiB per field is the smallest common limit (nginx `large_client_header_buffers 4 8k`, Apache `LimitRequestFieldSize 8190`, Tomcat `maxHttpHeaderSize 8192`); Node.js 16 KiB total; Cloudflare 128 KB total; CloudFront 32 KB request; AWS ALB 16 K per header; Vercel 16 KB per header. Budget for one RQP request header: 4 KiB. Full SHA-256 digests of 256 blocks need about 11–14 KB in any Structured Field encoding, so they do not fit. `sf-key` cannot start with a digit (our ids can). A truncated digest in the request is safe because `r1.` binds the full block hashes: the client recomputes the page revision after a patch and loads the full document on a mismatch. Caching: Cloudflare ignores `Vary` by default; `Vary` on a per-client header gives no reuse; deltas must not be stored. QUERY (RFC 10008) has no verified browser or CDN support. Sources: report of R-6 in this record's progress log.

### Human decisions (2026-10-12)

| ID | Question | Decision |
|---|---|---|
| H-44 | Q-S2-1: client block-digest header | **`Rq-Have`**, a Structured Field Dictionary: `t` = the client's template revision (Token, `t1.…`), `b` = Byte Sequence of the concatenated **64-bit prefixes** (first 8 bytes) of the block SHA-256 digests, in template block order. 256 blocks ≈ 2.8 KB, within the 4 KiB budget; no size fallback is needed. Integrity: the client checks `next_revision` after the patch; a prefix collision only causes a full load |
| H-45 | Q-S2-2: caching | A delta has `Cache-Control: no-store` and no ETag. A full document has a strong `ETag` equal to `"r1.…"`, is the same for all clients (manifest always inline, H-1), and has no `Vary` on `Rq-*` headers; it keeps the normal cache policy of the page. `304` by `If-None-Match` |
| H-46 | Q-S2-3: client's current page revision | Standard **`If-None-Match: "r1.…"`**. It gives `304` and is the `base_revision` of a delta. The draft header `Rq-Base-Revision` is removed |
| H-47 | T-02 Q-T02-1/2: patch operations | **Only `replace_block`.** `insert_block` and `remove_block` are removed (a new block means a new template and a full document; `remove_block` equals `replace_block` with empty content). New operations later need a capability |
| H-48 | T-02 Q-T02-3/4: client checks | **The client runs the markup analysis** on the original document and compares blocks and revisions with the manifest (MUST), and runs it again on the patched document; plus the fail-closed attribute rule for patched content (`on*` names, `javascript:` after removal of tab/LF/CR and leading C0/space, any `&` other than `&amp;` → reject) |
| H-49 | T-02 Q-T02-5/6: origins and manifest position | Schema accepts `http` and `https`; the client allows `http` only in a debug build with an explicit app flag; release builds use `https` only. The manifest is inserted exactly before the first `</head>` end tag in HTML context; without it the document is sent without RQP |
| H-50 | T-02: error codes and manifest limit | **Accepted:** `MANIFEST_INVALID`, `PATCH_INVALID` (Protocol → normal load), `PATCH_CONTENT_REJECTED` (SecurityViolation → normal load + metric); `maxManifestBytes` 64 KiB |
| H-51 | T-01 Q-H1: response to a non-RQP request | **The same full document F** for every request (inline manifest, `Rq-Version: 1`, ETag `r1.`); no `Vary` |
| H-52 | T-01 Q-H2: strong ETag and content coding | **The server MUST send a weak ETag `W/"r1.…"` whenever it applies a content coding**; a strong ETag only for the identity coding. A delta base is accepted from a weak tag (safe through the `next_revision` check) |
| H-53 | T-01 Q-H3: shape of `Rq-Capabilities` | **Inner List of Tokens as in ADR-006**: `Rq-Capabilities: (block-patch realtime-ws)`. Any other shape (also a field split over two lines) → treated as absent (no delta) |
| H-54 | T-01 Q-H4: withdrawals | **Removed:** capability tokens `manifest` and `json-blocks`; response headers `Rq-Revision` and `Rq-Template-Revision` |
| H-55 | T-05 Q-T05-1: `policy`/`limits` and the strong ETag | **Bind them into `r1.`**: the page-revision preimage gets a line with a deterministic text form of `policy` and `limits` (no JSON canonicalization, H-11). When both are absent the line is absent, so earlier values stay the same |
| H-56 | T-05 Q-T05-2: `on*` attributes in a changed block | **The server SHOULD send the full document** when a changed html block fails the client attribute rule (one request instead of two); the client check stays (fail closed); the guide advises against `on*` in blocks |
| H-57 | T-06 Q-T06-1/2: policy change and wire format | **Accept and document** the one extra full load per client after a policy or limits change (INTEGRITY_ERROR from such a delta is not an attack); the encoding of the policy line (DL-027) is **confirmed as is** |
| H-58 | Security review S2 L1+L2: response binding on the client | **Tighten both.** A `304` is accepted only for a request that sent `If-None-Match: "R"` and only when its ETag (if present) weakly matches R; else normal load. A manifest or delta is bound to the full cache key of the final URL (with query and partition); release builds do not accept a manifest or delta from a final URL that is not `https`. Fixtures for each case |
| H-59 | Security review S2 L3: attribute rule | **Deny `data:` and `vbscript:`** like `javascript:` (same normalization); reword the claims to "no inline event handlers and no dangerous URL schemes in patched content"; framework script gadgets are controlled by CSP (SEC-04) |
| H-60 | Security review S2 L4: privacy of digests | **Document** that `Rq-Have` and `If-None-Match` expose unkeyed digests in intermediary header logs and recommend excluding them from such logs until keyed revisions (WP-18); **new cache rule:** clearing cookies or site data deletes the snapshots of that site. `b` stays for private pages |
| H-61 | Security review S2 L5: public partition | **Require an explicit `Cache-Control: public`** (or a request without credentials) for the `public` partition; reword "policy can only make the client stricter" precisely |
| H-62 | Security review S2 round 2: L1 full document off the allowlist, L2 unknown credentials, L3 non-UTF-8 decoding | **Fix all three in S2.** (1) The client stores F only when the final request carried RQP fields (its origin is in the allowlist, RQP-05). (2) Unknown credentials count as present: the client treats a request as credentialed unless it knows that no cookie (also from the WebView cookie store), `Authorization`, HTTP authentication or client certificate was used; a `Set-Cookie` in the response also counts. (3) UTF-8 only: a page whose `Content-Type` charset is not a UTF-8 label is invalid for RQP (passthrough); F gets `charset=utf-8` when A has no charset; the client accepts F only as UTF-8 (charset label or UTF-8 BOM) |
