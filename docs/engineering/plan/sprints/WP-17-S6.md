### Human decisions

| ID | Question | Decision |
|---|---|---|
| H-103 | Q-A: the content of the manifest (`evidence/rqp-bytes/report.md` §5, §8) | **M3 + M1:** the manifest is `protocol`, `origin`, `path`, `page_revision`, and `policy` and `limits` only with members that are not the default (a default member is not written); no `blocks` list and no `template_revision`: the client computes them (H-44, H-48) and checks only the page revision; after that check it uses its computed template revision and digests (also for `Rq-Have`). Replaces the manifest members of H-44 and the text of manifest-patch §1.3 rule 3 |
| H-104 | Q-B: the delta envelope | **DC1:** `{"next_revision": …, "operations": [{"block_id": …, "content": …}]}`; no per-operation hash (replaces H-10), no `base_revision`, no `template_revision`, no `type`/`protocol`, no `op`/`format`; integrity by `next_revision` (step 7); the mismatches of steps 1 and 2 become `INTEGRITY_ERROR` at step 7 (the error catalog of H-50 changes) |
| H-105 | Q-C: further compaction | **None in `rqp/1`:** no short member names, no URL in the revision preimage, no array envelope, no CBOR, no truncation |
| H-106 | Q-D: `Rq-Have` prefix length | **64 bits, as now** |
| H-107 | Security review S6 F1 (medium): without `base_revision` (H-104) a delta applies to every snapshot that equals its target outside the operations: silent rollback, stale pinning, cross-user and cross-URL content through a shared cache that ignores `no-store` (T-05); the byte study had rated D2 "diagnostic", which was wrong | **A delta binding value, 0 bytes:** the envelope member `next_revision` is replaced by `binding` = `d1.` + B64U(SHA-256(`rqp-d1` LF U LF B LF R′ LF)), where U is the canonical cache-key URL of the request (H-58), B the base page revision (server: the strong `If-None-Match` value; client: its snapshot revision) and R′ the next page revision (the client computes it, step 7). Equal values give equal U, B and R′; a mismatch is `INTEGRITY_ERROR` at step 7. The page revision preimage does not change (H-105 stays). Replaces the `next_revision` member of H-104 |
| H-108 | Security re-review B1 (medium): after H-107 a delta still applies to every request with the same base B and URL U; an attacker can choose B (a public page revision) and get a delta built for their session stored by a cache that ignores `no-store`; A→B→A content gives a rollback (B2) | **A client nonce:** every delta-eligible request carries a fresh random 16-byte nonce N in `Rq-Have` (member `n`, an SF Byte Sequence; a new value from a CSPRNG for every request, never reused); the binding preimage becomes `rqp-d1` LF U LF B LF N LF R′ LF (N as base64url without padding); a server sends a delta only when the request has a valid `n` (else F); a stored delta matches no other request. Cost: about 24 request header bytes per delta navigation, 0 response bytes |
| H-109 | The nonce inside `Rq-Have` makes the whole field new on every request, so HPACK cannot reuse `t` and `b` on a warm HTTP/2 connection (a repeat revisit: 164 header bytes instead of 60) | **A separate request field `Rq-Nonce`:** an SF Item, a Byte Sequence of exactly 16 bytes (parameters ignored), fresh per delta-eligible request; `Rq-Have` keeps only `t` and `b`; the binding uses the same N; a server sends a delta only with exactly one valid `Rq-Nonce` (else F). Replaces the member `n` of H-108; the security of H-108 is unchanged |
