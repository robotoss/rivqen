# Legacy golden fixtures

<!-- SPDX-License-Identifier: Apache-2.0 -->
<!-- SPDX-FileCopyrightText: The Rivqen Authors -->

Golden fixtures for the server side of the legacy (VasSonic-compatible) protocol: one request to the server under test and the exact expected response. Every server (the Rust reference server of WP-03, the Node.js, Java and PHP SDKs) runs them with `server/conformance`. Catalog: `docs/engineering/protocol/fixtures.md` §3. Behavior: `docs/engineering/protocol/legacy-wire.md` §10 (rules C-01 to C-16). Profiles: ADR-005. Format fixed by the architect for WP-02 S1 (DL-067, DL-068). The client part of each fixture (`cache-before`, expected actions) is added before P3 (H-110).

Upstream: `Tencent/VasSonic` at `59936beff656d4b5718ff6444d6c5e001a2c5231`. Clean-room: no upstream code, comments, test code or sample HTML in this directory. The pages are Rivqen test pages.

## Layout

```text
fixtures/legacy/
├── pages/<page-id>.html            # application body bytes, exact
└── FX-LEG-<NAME>[--<JAVA|NODE|PHP>]/
    ├── case.json                   # written by a person
    └── expected.json               # generated by tools/legacy-fixtures/gen.mjs; never edited by hand
```

`FX-LEG-<NAME>` is a canonical fixture (`legacy-canonical`). `FX-LEG-<NAME>--JAVA` (or `--NODE`, `--PHP`) is a profile fixture: it replaces `FX-LEG-<NAME>` in the runs of that profile (DL-068).

## Canonical `case.json`

```json
{
  "id": "FX-LEG-DATA-CHANGE",
  "description": "Same template, data changed: data-only response",
  "profile": "legacy-canonical",
  "rules": ["C-06", "C-07", "C-11"],
  "upstream": { "repo": "Tencent/VasSonic", "sha": "59936beff656d4b5718ff6444d6c5e001a2c5231" },
  "sources": ["upstream:sonic-java/src/main/java/com/github/tencent/SonicFilter.java:105-144"],
  "evidence": "trace",
  "traces": {
    "legacy-java": "evidence/traces/server/java/S06-data-change.http",
    "legacy-node": "evidence/traces/server/node/S06-data-change.http",
    "legacy-php": "evidence/traces/server/php/S06-data-change.http"
  },
  "page": "b",
  "app": { "status": 200, "headers": [["content-type", "text/html; charset=utf-8"]] },
  "request": {
    "method": "GET",
    "headers": [
      ["accept-encoding", "gzip"],
      ["accept-diff", "true"],
      ["if-none-match", "{{etag:a}}"],
      ["template-tag", "{{tag:a}}"]
    ]
  }
}
```

| Field | Rule |
|---|---|
| `id` | The directory name |
| `profile` | `legacy-canonical` |
| `rules` | Rules of legacy wire §10 (`C-01`…`C-16`) that the case checks |
| `upstream` | Always the pinned repository and SHA above |
| `sources` | At least one `upstream:<path>:<line>` or `docs:<page>#<anchor>` reference |
| `evidence` | `trace` (the scenario was captured from the upstream servers) or `code-reading` |
| `traces` | Only with `evidence: trace`: the stored trace of the same request for each upstream profile |
| `page` | The application body: `pages/<page>.html` |
| `app` | The application response before the legacy step: status and field lines (lower-case names, order kept); default `{ "status": 200, "headers": [["content-type", "text/html; charset=utf-8"]] }` |
| `request.method` | Default `GET` |
| `request.target` | Default `https://shop.example.com/catalog` |
| `request.headers` | Field lines in order; a name can repeat (one line each). Placeholders below |
| `level` | Optional, `must` (default) or `should` |

**Placeholders** (the only computed values; every other byte is literal):

| Placeholder | Value |
|---|---|
| `{{etag:<page>}}` | Lowercase hex SHA-1 of `pages/<page>.html` (C-04) |
| `{{ETAG:<page>}}` | The same in uppercase hex |
| `{{tag:<page>}}` | `template-tag` of the page under the profile of the fixture (C-08 for `legacy-canonical`); the empty string when the profile sends no `template-tag` for that page |
| `{{TAG:<page>}}` | The same in uppercase hex |

A placeholder can be part of a value, for example `"\"{{etag:a}}\""` or `"W/\"{{etag:a}}\""`.

## Profile `case.json`

```json
{
  "id": "FX-LEG-DATA-CHANGE--JAVA",
  "description": "legacy-java: HashMap order and Gson escaping of the data body; Cache-Control no-cache",
  "profile": "legacy-java",
  "replaces": "FX-LEG-DATA-CHANGE",
  "divergences": ["D-08", "D-09"],
  "sources": ["upstream:sonic-java/src/main/java/com/github/tencent/SonicFilter.java:60-149"],
  "trace": "evidence/traces/server/java/S06-data-change.http"
}
```

A profile fixture takes `page`, `app` and `request` of the replaced fixture; the placeholders are resolved under its own profile. Optional `not_reproduced`: the profile does not reproduce this unsafe upstream behavior (DL-069, DL-082). It takes only `"U-11"` or `"U-13"`, and each has its own check: the generator checks that the trace shows the documented difference, not that it equals the expected response (see `tools/legacy-fixtures/README.md`). The profile fixtures of S24 to S27 (`REDIRECT`, `PASS-NOT-FOUND`, `PASS-POST`, `PASS-HEAD`) have `not_reproduced: "U-13"` and expect the C-01 pass-through.

## `expected.json`

Generated.

```json
{
  "id": "FX-LEG-DATA-CHANGE",
  "profile": "legacy-canonical",
  "level": "must",
  "request": { "method": "GET", "target": "https://shop.example.com/catalog", "headers": [["accept-encoding", "gzip"], ["accept-diff", "true"], ["if-none-match", "3e31…"], ["template-tag", "3c77…"]] },
  "status": 200,
  "fields": {
    "etag": ["4c33…"],
    "template-tag": ["3c77…"],
    "template-change": ["false"],
    "cache-offline": ["true"],
    "cache-control": ["no-cache, private"],
    "content-type": ["text/html; charset=utf-8"],
    "sonic-etag-key": [],
    "cdn-cache-control": [],
    "surrogate-control": [],
    "vary": ["template-tag"]
  },
  "body": { "kind": "data", "data": { "{title}": "<title>Shop</title>", "{price}": "…" }, "template_tag": "3c77…", "html_sha1": "4c33…", "diff": "" },
  "split": { "applied": true, "template_sha1": "3c77…", "keys": ["{title}", "{price}", "{stock}"], "rebuild_sha1": "4c33…" },
  "profiles_same": ["legacy-php"]
}
```

| Member | Rule |
|---|---|
| `fields` | For each listed name, the exact list of field values in order (one per field line; names compare case-insensitively). `[]` means the field must be absent. Names not listed are not compared, except `Content-Length` (equal to the body length when present) and `Content-Encoding` (absent or `gzip`, DL-073; the runner decodes `gzip` first) |
| `body.kind` | `page` (exactly the bytes of the application body), `data` (a JSON object with exactly the members `data`, `template-tag`, `html-sha1`, `diff`; compared as JSON values, D-08), `none` (no body) |
| `split` | The template and data split of the page under the profile: `applied` (false when the profile does not split), `template_sha1`, `keys` in order, `rebuild_sha1` (SHA-1 of the template with each placeholder replaced once by its value, in template order; equals the etag when the split is consistent). For core and SDK unit tests; the runner does not use it |
| `profiles_same` | Canonical fixtures only: the upstream profiles whose stored trace gives this exact expected response (no profile fixture needed) |
| `trace` | Profile fixtures only: copied from `case.json` |

The runner with `--profile legacy-canonical` runs every canonical fixture. With `--profile legacy-java` (or node, php) it runs the canonical fixtures that list that profile in `profiles_same` and the profile fixtures of that profile: only behavior confirmed by an upstream trace (DL-068).

## Generator checks (`gen.mjs --check`)

1. Every `expected.json` equals the regenerated one byte for byte; no unknown or missing files.
2. Every trace-backed profile response (status, the fields `etag`, `template-tag`, `template-change`, `cache-offline`, `cache-control`, `content-type`, `sonic-etag-key`, and the decoded body: exact for `page`, as JSON values for `data`) equals the stored trace, except a fixture with `not_reproduced`, which gets the check of its item. `content-type` is compared on every response (also a `304`) as a media type, not byte for byte. The request equals the trace request: by method and field lines, and for a trace with a `Host` first line (S22 to S29) also by authority and path. `vary`, `cdn-cache-control` and `surrogate-control` are not compared with the traces: every profile follows C-13 and C-15 (U-12, H-111).
3. `OVERRIDE_NOT_NEEDED`: a profile fixture whose expected response equals the canonical one. A fixture with `not_reproduced` is skipped: a U-13 fixture expects the canonical pass-through, and check 2 proves that its trace differs.
4. `OVERRIDE_MISSING`: a trace-backed canonical fixture whose trace for a profile differs from the canonical expected response, with no profile fixture.
5. Every `rules` item exists in legacy wire §10; every C-rule is covered by at least one fixture.

## Client fixtures

Format of the client part (WP-01 S2 T-01; decisions DL-101, DL-104, DL-110, DL-111, DL-112). A client fixture gives a legacy client the application responses, the cache before the run and a schedule of steps. Its `expected.json` is the observable result of DL-110: the requests, the web view actions, the page messages, the final codes, the cookie calls and the cache snapshots. The canonical result follows the rules `CL-01`… of `docs/engineering/protocol/legacy-client.md` §9. The Rivqen JavaScript client model in `tools/legacy-fixtures` writes `expected.json`; `gen.mjs --check` compares every `legacy-android` result with the stored upstream client trace in `evidence/traces/client/android/` (DL-104). Status: format fixed; the model is task T-04, the fixture files are task T-06.

Clean-room: a client fixture describes observable effects only. It names no upstream class, method, flag or file. The upstream cache files (D-42) are not part of a fixture: the cache is an abstract record.

### Client layout

```text
fixtures/legacy/
├── pages/<page-id>.html                 # shared with the server fixtures; empty.html has 0 bytes
├── FX-LEG-CL-<NAME>-<Q|S>[--ANDROID]/
│   ├── case.json                        # kind "client"; written by a person
│   └── expected.json                    # generated by tools/legacy-fixtures/gen.mjs
└── functions/
    ├── cases.json                       # byte copy of tools/upstream-lab/client/functions.json
    ├── legacy-canonical.json            # generated
    ├── legacy-android.json              # generated
    └── legacy-ios.json                  # generated
```

| Name | Rule |
|---|---|
| `FX-LEG-CL-<NAME>-Q`, `-S` | Canonical client fixture (`legacy-canonical`) for Quick (`quick`) or Standard (`standard`) presentation. One mode per fixture |
| `<NAME>` | A catalog name of `docs/engineering/protocol/fixtures.md` §3 without `FX-LEG-` and with an optional variant (`INTERRUPTED-STREAM`, `INTERRUPTED-BEFORE`), or a scenario ID without the hyphen (`CS04`, `CS13A`) |
| `FX-LEG-CL-<NAME>-<Q\|S>--ANDROID` | Profile fixture `legacy-android`. It replaces the canonical fixture in the `legacy-android` runs (DL-111). Only for a canonical fixture with `evidence: trace` |
| `functions/` | Function fixtures: one generated file per profile, one shared case file |

The client fixtures and the server fixtures share `pages/` and the directory. `kind: "client"` in `case.json` separates them; a server `case.json` has no `kind`.

| `responses` | object | The application responses, by name (1 to 32). Name: 1 to 32 characters of `a-z`, `0-9`, `-`. Entry: table below |
| `cache_before` | array | The cache before the first step (0 to 16 entries). Entry: table below. Must be `[]` with `evidence: trace` (the lab starts each run with an empty app state) |
| `schedule` | array | Steps and `case` entries in order (1 to 256 steps). Rules below |
| `level` | string | Optional, `must` (default) or `should` |

`config` keys are the keys of the Android harness (`tools/upstream-lab/android/README.md`). Defaults are the harness defaults. Their effect on the canonical result is rule CL-03.

| Key | Type | Default |
|---|---|---|
| `account` | string or `null` | `"rq-test-account"` |
| `cookie` | string or `null` | `null` |
| `network_valid` | boolean | `true` |
| `accept_diff` | boolean | `true` |
| `account_related` | boolean | `true` |
| `reload_in_bad_network` | boolean | `false` |
| `support_cache_control` | boolean | `false` |
| `support_local_server` | boolean | `false` |
| `auto_start` | boolean | `true` |
| `get_cookie_when_session_create` | boolean | `true` |
| `cache_verify_with_sha1` | boolean | `true` |
| `unavailable_time_ms` | integer, 0 to 86 400 000 | `21600000` (6 h) |
| `connect_timeout_ms`, `read_timeout_ms` | integer | `5000`, `15000` |

Synthetic values only: accounts `rq-test-account`, `rq-test-account-2`; cookies `session=rq-test-cookie-<n>`.

**`responses` entry.** Exactly one of these forms:

| Form | Rule |
|---|---|
| `{ "page": "<page-id>", "app": { "status": 200, "headers": [[name, value], …] } }` | `page` names `pages/<page-id>.html`. `app` as in a server `case.json`; the same default |
| `{ "fixture": "FX-LEG-<NAME>" }` | The `page` and `app` of that canonical server fixture. Its `request` is not used: the client model makes the request |

The server model of `server_profile` (`respond` in `src/model.mjs`) answers each request of the client model with the current response entry (the last `case` entry before the request). The answer is the same for the same request, so the server response is not written twice (DL-112).

**`schedule`.** Each item is one of these:

| Item | Rule |
|---|---|
| `{ "case": "<name>" }` | Sets the current application response for the next requests (the `case` of a scenario, CONTRACT §2). It is not a step: it has no number and no trace event. A `case` entry must come before the first step that sends a request |
| `{ "do": "<step word>", … }` | One step of CONTRACT §3, with the members of that step word (`point`, `bytes`, `name`, `value`, `valid`, `for`, `timeout_ms`, `ms`) and the optional `session` (1-based index of the opened sessions) and `wait_ms` (`request_resource`). The S2 conductor steps are step words too: `set_body_member` (`name`, `value`; a body fault on the next exchange) and `case` (`value`: the form of a scenario `case`, `page` with optional `status` and `headers`; the application response of every later exchange; unlike a `case` entry it is a numbered step). An unknown word or member is a case error |

Steps are numbered from 1 in schedule order; `case` entries are not counted. For `evidence: trace`, the steps must equal the `step` objects of the `step.start` events of the trace without their `seq` member, in order (check 7). There is no macro: write the steps of `first_load` out. Reason: the macro changed between S1 (free order) and S2 (fixed order), and a trace keeps the steps that ran. A WebView run (`webview: true`, CS-19) has no client fixture.

Limits (a case error, not a crash): at most 256 steps, 16 `create_session` steps, 32 responses, 16 `cache_before` entries; `settle.ms` and `timeout_ms` from 0 to 3 600 000; `bytes` from 0 to the length of the page body; `wait_ms` from 0 to 30 000.

**`cache_before` entry.** The generator expands each entry into the cache record of CL-38: the record that a canonical first load of the page from `server_profile` would commit (CL-25, CL-41). Optional members change the record, for example for an integrity test (CL-40).

| Member | Type | Rule |
|---|---|---|
| `page` | string | Required. A page of `pages/` |
| `partition` | string or `null` | Default: `config.account` |
| `url` | string | Default: the fixture `url` |
| `vary` | array of `[name, value]` | Default `[]` (CL-12) |
| `fields` | array of `[name, value]` | Replaces the stored page fields (CL-21) |
| `etag`, `template_tag` | string | Replaces the stored value |

Top level:

| Member | Rule |
|---|---|

| `client` | The projection: `sessions`, then `phases` |
| `profiles_same` | Canonical fixtures only: `["legacy-android"]` when the trace projection equals this `client` member (no profile fixture needed), else `[]` |

`client.sessions`: one entry for each `create_session` step, in step order.

| Member | Rule |
|---|---|
| `step` | The number of the `create_session` step |
| `opened` | `false` when no session opened (CL-07, CL-08) |
| `session` | Only when `opened`: the 1-based index among the opened sessions (the `session` of the steps and events) |
| `partition` | The account at that step (CL-05) |
| `url` | The page URL |

`client.phases`: the schedule split as in the outcome projection (DL-104, CONTRACT §6): a phase ends with a `settle` step; the next step starts a new phase. Every phase has all members below, also when a list is empty.

| Member | Content | Order in the file and in the comparison |
|---|---|---|
| `steps` | `[first, last]` step numbers of the phase | — |
| `requests` | The requests that reached the server in the phase | `exchange` order |
| `cookies` | The cookie calls | Sorted (multiset) |
| `actions` | `load_url`, `load_data`, `message`: the web view calls of the session on the main thread | Exact order |
| `intercepts` | The answers to intercepted main-document requests | Sorted (multiset) |
| `results` | The codes of each session at its `destroy` step | Sorted (multiset) |
| `snapshots` | One entry for each `snapshot_cache` step | Step order |

"Sorted" means: sorted by the canonical JSON text of each entry (keys in the order of this page, no white space). The entry forms:

| Entry | Members in order |
|---|---|
| request | `exchange` (1-based, all sessions), `method`, `target` (path and query), `fields`, `response` |
| request `fields` | The request field lines whose lowercase name is `accept-diff`, `if-none-match`, `template-tag`, `cookie` or `sonic-sdk-version`, in sent order, names in lowercase. Other fields (`accept-encoding`, `user-agent`, `host`, …) are transport and are not listed |
| `response` | `status`; `fields`: the delivered lines whose lowercase name is `etag`, `template-tag`, `template-change`, `cache-offline`, `sonic-etag-key` or `set-cookie`, in order, names in lowercase; `complete`: `false` when the body ended with an error (`cut`, reset). After `set_field` or `drop_field` the delivered form counts |
| cookie | `{ "call": "get", "url", "value" }` (`value` string or `null`) or `{ "call": "set", "url", "values" }` (`values`: the `Set-Cookie` values in order) |
| `load_url` | `do`, `session`, `url` |
| `load_data` | `do`, `session`, `url` (the base URL), `fields`, `body_len`, `body_sha256` |
| `message` | `do`, `session`, `json`: the message text without the member `local_refresh_time` (CONTRACT §6 normalization) |
| intercept | `session`, then `{ "null": true }`, or `status`, `fields`, `body_len`, `body_sha256`, `complete` |
| result | `session`, `src_code`, `final_code` |
| snapshot | `entries`: the cache records (CL-38), sorted by `partition`, `url`, `vary` |
| cache record | `partition`, `url`, `vary`, `etag`, `template_tag`, `page_sha256`, `template_sha256`, `data_sha256`, `fields` |

Value rules:

1. `body_len` and `body_sha256` are the length and the lowercase hex SHA-256 of the decoded body bytes that the web view gets (UTF-8 for `load_data`). For an incomplete stream (`complete: false`) they are the bytes before the error.
2. `fields` of `load_data`, of an intercept and of a cache record are `[name, value]` pairs, names in lowercase, sorted by name (a stable sort keeps the order of lines with one name).
3. `page_sha256` and `template_sha256` are the SHA-256 of the UTF-8 page and template; `data_sha256` is the SHA-256 of the UTF-8 compact JSON text of the stored block map, in stored key order. A member is `null` when the record has no such part. `etag` and `template_tag` are the stored strings, or `null`.
4. `vary` is a list of `[name, value]` (lowercase names, sorted; `value` `null` for an absent field), `[]` when the response had no `Vary` member that counts (CL-12).
5. URLs are absolute. Hashes are lowercase hex.

### Trace projection and the comparison (DL-104)

For `legacy-android`, the generator makes the same `client` member from each stored run of the trace (`run-<k>.jsonl` and the `.http` files). All runs must give the same projection; else the case is not trace-backed (check 7). The projection uses the phases of `settlePhases` in `tools/upstream-lab/client/src/determinism.mjs` (import, not a copy).

| Member | From the trace |
|---|---|
| `sessions` | Each `create_session` step and the `session.created` event in its phase: `session_id` `null` → `opened: false`. `partition`: the account of the run at that step (`config.account`, then the `set_account` steps) |
| `requests` | `proxy.request` (method, target, fields), `proxy.response_head` (status, delivered fields), `proxy.response_end` (`complete`). A refused connection (`server_down`) has no exchange |
| `cookies` | `runtime.cookie_get` (`value`); `runtime.cookie_set` (`value`: a string, `null` or a list → `values` list) |
| `actions` | Harness events of the `main` thread in `hseq` order: `client.load_url`, `client.load_data` (`base_url` → `url`, `headers` → `fields`), `session.message` (`json`, normalized) |
| `intercepts` | `client.intercept`: `"null": true`, or `status`, `headers`, `body_len`, `body_sha256`, `complete` |
| `results` | `session.result` |
| `snapshots` | `cache.snapshot`. The files of one stem form one record. The stem equals the `session_id` of a session of the run; that session gives `partition` and `url`. `.html` → `page_sha256`, `.tpl` → `template_sha256`, `.data` → `data_sha256`, `.header` `text` (lines `<name> : <value>`) → `fields`, and its `etag` and `template-tag` lines → `etag`, `template_tag`. A stem with no session is a projection error. A file `<stem>.html.tmp` (the rebuilt page that failed the `html-sha1` check, CS-28) is a work file, not part of a record: the projection does not use it, but its stem must be a session id of the run (DL-122). `vary` is `[]` |

Normalization before the comparison:

1. URLs: the lab prefix `http://10.0.2.2:18090/` becomes the origin and path of the fixture `url` (the lab page URL is the fixture URL).
2. `fields` of `load_data`, of an intercept and of a record, in the trace and in `expected.json`: remove the transport fields `date`, `connection`, `keep-alive`, `transfer-encoding`, `content-length`, `content-encoding` and every name that starts with `x-android-`, and the fields that no server model reproduces from the traces: `vary`, `cdn-cache-control`, `surrogate-control` (as server check 2, U-12).
3. An intercept with `complete: false`: `body_len` and `body_sha256` are not compared. They depend on the content coding of the lab server (CS-13a: 128 wire bytes, 139 decoded bytes).
4. A record: `data_sha256` compares as present or `null` only. The upstream data file has its own form (D-35, D-42), and the trace has its hash only.
5. `content-type` in the `fields` of `load_data`, of an intercept and of a record, in the trace and in `expected.json`: the value compares as a media type (DL-119), with the form of server check 2: the type, the subtype, the parameter names and the `charset` value in lower case (RFC 9110 §8.3), no white space around `;` and `=`, one pair of quotes removed, the parameter order kept. The Tomcat form `text/html;charset=utf-8` of the `lab-java` traces (CS-08, CS-10) equals `text/html; charset=utf-8`. Another type, subtype, charset or parameter is a difference. `expected.json` keeps the value of the model.

Then the two `client` members must be equal member for member, with the order of the table "client.phases" (exact order, exchange order, multiset or step order).

### Write a client fixture

1. Find the behavior in legacy client §9. Write down its CL rule.
2. Find a stored scenario with the same behavior in `tools/upstream-lab/client/scenarios.json`. If one exists, use `evidence: trace`, the scenario ID and the mode.
3. Copy the steps of the trace (`step.start` events) into `schedule`. Put a `case` entry before the steps that use a new application response.
4. Write `responses` with the pages and application responses of the scenario.
5. If no scenario exists, use `evidence: code-reading` and `server_profile: legacy-canonical`. Write `cache_before` instead of a setup load if you need a cache.
6. Run `node tools/legacy-fixtures/gen.mjs`. Read the new `expected.json` against the CL rules.
7. If check 9 reports `OVERRIDE_MISSING`, write the `--ANDROID` profile fixture with the divergences that cause the difference.
8. Run `node tools/legacy-fixtures/gen.mjs --check`.
9. Do not change `case.json` to make the model pass. Report a model error to the model owner.

## Rules

1. Files are exact bytes (`.gitattributes`: `fixtures/** -text`).
2. A fixture changes only with review by the protocol owner. Never change a fixture to make an implementation pass.
3. One behavior per fixture.
4. No real user data, tokens or domains. Use `example.com`.
