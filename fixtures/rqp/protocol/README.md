Golden fixtures for RQP negotiation, manifest and patch (`docs/engineering/protocol/negotiation.md`, `manifest-patch.md`). A server SDK and the server demo must give the expected response for every case before SDK code is written (WP-17 acceptance). Format fixed by the architect for WP-17 S2. Catalog: `docs/engineering/protocol/fixtures.md` §4.1.

## Layout

```text
fixtures/rqp/protocol/
├── pages/<page-id>.html          # application page bytes, exact (generated pages by recipes in tools/rqp-protocol/src/pages.mjs)
└── FX-RQ-<P|C><NN>-<NAME>/       # P = server case, C = client case; variants of one catalog row share NN
    ├── case.json                 # written by a person
    ├── expected.json             # generated by tools/rqp-protocol/gen.mjs; never edited by hand
    └── response.body             # client cases with a body only: generated exact bytes
```

## `case.json`

```json
{
  "id": "FX-RQ-P09-DELTA",
  "description": "Delta with only the changed block",
  "rules": ["RQP-08", "RQP-11"],
  "page": "page-b",
  "client_page": "page-a",
  "app": { "status": 200, "headers": [["content-type", "text/html; charset=utf-8"], ["cache-control", "no-cache"]] },
  "request": {
    "method": "GET",
    "headers": [
      ["rq-version", "1"],
      ["rq-capabilities", "(block-patch)"],
      ["accept", "text/html, application/vnd.rivqen.delta+json"],
      ["if-none-match", "{{r1:page-a}}"],
      ["rq-have", "t={{t1:page-a}}, b={{have:page-a}}"]
    ]
  }
}
```

| Field | Rule |
|---|---|
| `page` | The page the application renders now (`pages/<id>.html`) |
| `client_page` | Optional. The page the client holds; used only by placeholders |
| `app` | The application response before the RQP server step: status and header lines (lower-case names, order kept) |
| `request.headers` | Header lines in order; a name can repeat (one line each). Placeholders: `{{r1:<page>}}` → `"r1.…"` (with quotes), `{{t1:<page>}}` → `t1.…` (Token), `{{have:<page>}}` → `:<base64>:` of the 64-bit prefixes (H-44). The generator replaces them; the harness gets the final bytes in `expected.json` |

Optional members: `request.target` (default `https://shop.example.com/catalog`), `server_config` (`policy`, `limits` of the server manifest), `client_members` (`policy`, `limits` of the client snapshot; the `{{r1:…}}` placeholder then includes the H-55 policy line), `level` (`"should"` for a case that checks a SHOULD rule, for example P-35 / H-56; a conforming server can fail it and must say so).

Placeholders are the only computed values in `case.json`. Every other byte is literal.

Client cases (`kind: "client"`): `context` (snapshot page and members, build type), `response` (status, header lines and a body recipe). Format in `tools/rqp-protocol/README.md` (section "Client case.json").

## `expected.json`

Generated. Server cases: `request` (`method`, `target`, final header lines), optional `server_config`, `status`, `headers_required` (name → exact value), `headers_forbidden` (names), `body`: `{"kind": "full", "insert_at", "manifest"}` (the page with the manifest inserted; the manifest is compared as a JSON value, fixtures.md §5), `{"kind": "delta", "base_revision", "next_revision", "template_revision", "blocks": [{"id", "format", "sha256"}]}` (changed blocks in order), `{"kind": "app"}` (the application body unchanged) or `{"kind": "none"}`.

Client cases: `context`, `request`, `response` (with `body`, `body_bytes`, `body_sha256`), `result` (`outcome`, `error`, `next`, `metric`, `snapshot`).

Harness: `tools/rqp-protocol/check.mjs` runs a server module `handle(request, appResponse, pageBytes, config)` or a client module over the fixtures. The public origin is `https://shop.example.com`; there is no content coding.

## Rules

1. Files are exact bytes (`.gitattributes`: `fixtures/** -text`).
2. A fixture changes only with review by the protocol owner. Never change a fixture to make an implementation pass.
3. One behavior per fixture.
4. No real user data, tokens or domains. Use `example.com`.
5. Block analysis of pages uses the RQP markup rules; the generator may call the Node.js markup candidate (`tools/rqp-markup/node/src/cli.mjs`).
