# RQP protocol fixtures

<!-- SPDX-License-Identifier: Apache-2.0 -->
<!-- SPDX-FileCopyrightText: The Rivqen Authors -->

Golden fixtures for RQP negotiation, manifest and patch (`docs/engineering/protocol/negotiation.md`, `manifest-patch.md`). A server SDK and the server demo must give the expected response for every case before SDK code is written (WP-17 acceptance). Format fixed by the architect for WP-17 S2. Catalog: `docs/engineering/protocol/fixtures.md` §4.1.

## Layout

```text
fixtures/rqp/protocol/
├── pages/<page-id>.html          # application page bytes, exact (generated pages by recipes in tools/rqp-protocol/src/pages.mjs)
└── FX-RQ-<P|C><NN>-<NAME>/       # P = server case, C = client case; variants of one catalog row share NN
    ├── case.json                 # written by a person
    ├── expected.json             # generated by tools/rqp-protocol/gen.mjs; never edited by hand
    └── response.body             # client cases with a body only: generated exact bytes
```

## `case.json`

```json
{
  "id": "FX-RQ-P09-DELTA",
  "description": "Delta with only the changed block",
  "rules": ["RQP-08", "RQP-11"],
  "page": "page-b",
  "client_page": "page-a",
  "app": { "status": 200, "headers": [["content-type", "text/html; charset=utf-8"], ["cache-control", "no-cache"]] },
  "request": {
    "method": "GET",
    "headers": [
      ["rq-version", "1"],
      ["rq-capabilities", "(block-patch)"],
      ["accept", "text/html, application/vnd.rivqen.delta+json"],
      ["if-none-match", "{{r1:page-a}}"],
      ["rq-have", "t={{t1:page-a}}, b={{have:page-a}}"]
    ]
  }
}
```

| Field | Rule |
|---|---|
| `page` | The page the application renders now (`pages/<id>.html`) |
| `client_page` | Optional. The page the client holds; used only by placeholders |
| `app` | The application response before the RQP server step: status and header lines (lower-case names, order kept) |
| `request.headers` | Header lines in order; a name can repeat (one line each). Placeholders: `{{r1:<page>}}` → `"r1.…"` (with quotes), `{{t1:<page>}}` → `t1.…` (Token), `{{have:<page>}}` → `:<base64>:` of the 64-bit prefixes (H-44). The generator replaces them; the harness gets the final bytes in `expected.json` |

Optional members: `request.target` (default `https://shop.example.com/catalog`), `server_config` (`policy`, `limits` of the server manifest), `client_members` (`policy`, `limits` of the client snapshot; the `{{r1:…}}` placeholder then includes the H-55 policy line), `level` (`"should"` for a case that checks a SHOULD rule, for example the two P-35 cases / H-56 and H-59; a conforming server can fail it and must say so).

Placeholders are the only computed values in `case.json`. Every other byte is literal.

Client cases (`kind: "client"`): `context` (snapshot page, members and partition (`request`, the default, or `public`; H-65), build type; also `url`, `final_url` (default: `url`; differs after a redirect; both are parsed with the WHATWG URL parser, DL-040), `redirected` (default: `final_url` differs from `url`; `true` for a redirect to the same URL; a redirect result never goes to `public`, H-67), `allowlist` (a list of serialized origins; default: the origin of `url`; a case whose `final_url` has another origin must list `allowlist`, else the loader rejects it (DL-040); the client matches exactly, DL-038, DL-039; every entry must be equal to its own serialized origin, else the case is defective, H-69; **a redirect case must list `allowlist`**, code review round 4), `credentials` (`true`, `false` or `null`; `null` or absent = unknown, counts as present, H-62), `response_fields_visible` (default `true`: the reference client models a native fetch, so the C-24 cases from before H-64 keep their results; `false`: the client acts as if the response had a `Set-Cookie` field, H-64) `public_enabled` (default `false`: the app setting of the `public` partition is off, H-81; then a context snapshot in `public` is not used, DL-053) and `public_origin` (default `false`), H-58 and H-61), `response` (status, header lines and a body recipe; the default position is immediately after the head start tag of the document, H-72; the recipe option `manifest_position: "head-text"` puts the manifest before the first `</head>` bytes, and `manifest_after` immediately after a given text). Format in `tools/rqp-protocol/README.md` (section "Client case.json").

## `expected.json`

Generated. Server cases: optional `level` (`"must"` or `"should"`, copied from `case.json`), `request` (`method`, `target`, final header lines), optional `server_config`, `status`, `headers_required` (name → exact value), `headers_optional` (a `304` only: when the field is present, it is exactly one line with that value; today `rq-version: 1`, DL-036),  `headers_forbidden` (names: every `Rq-*` field of the application that the response does not have, DL-030, but `rq-version` is allowed on a `304`; `last-modified` for every outcome other than passthrough, DL-032), `body`: `{"kind": "full", "insert_at", "manifest"}` (the page with the manifest inserted; the manifest is compared as a JSON value, fixtures.md §5; since H-103 it has only `protocol`, `origin`, `path`, `page_revision` and the members of the server configuration that are not the default), `{"kind": "delta", "binding", "binding_inputs": {"url", "base_revision", "next_revision"}, "blocks": [{"id", "sha256"}]}` (H-104, H-107: `binding` is compared exactly; `binding_inputs` are U, B and R′ of the expected binding, for the diagnosis only; the changed blocks in order; `sha256` is the hash of the current content of the block, which the checker compares with the hash of the `content` that the server sent), `{"kind": "app"}` (the application body unchanged) or `{"kind": "none"}`.

Client cases: `context` (with every member above, the default values written out, also `redirected`; a context snapshot has its `partition`), `request`, `response` (with `body`, `body_bytes`, `body_sha256`), `result` (`outcome`, `error`, `next`, `metric`, `snapshot`). A snapshot has `url` (the canonical final URL) and `partition` (`request` or `public`); a client under test must return both.

Harness: `tools/rqp-protocol/check.mjs` runs a server module `handle(request, appResponse, pageBytes, config)` or a client module over the fixtures. It prints `FAIL [SHOULD]` lines for failed SHOULD cases and a summary `N passed, M failed, K SHOULD failed` (see `tools/rqp-protocol/README.md`). The public origin is `https://shop.example.com`; there is no content coding.

## Rules

1. Files are exact bytes (`.gitattributes`: `fixtures/** -text`).
2. A fixture changes only with review by the protocol owner. Never change a fixture to make an implementation pass.
3. One behavior per fixture.
4. No real user data, tokens or domains. Use `example.com`.
5. Block analysis of pages uses the RQP markup rules; the generator may call the Node.js markup candidate (`tools/rqp-markup/node/src/cli.mjs`).
